## 虚拟考核场景与题目条件

虚拟场景中负责人希望四周内将完成量提升到每小时 240 件，不增加硬件，由两名工程师交付一期。运营人员需要知道任务是否完成、为何等待，以及中断后能否接续。后续设备扩建时间和数量未定。可以建议调整目标与范围，但须说明依据和需要业务方决定的事项。

现场有 S1、S2 两个独立工位，每件完整周期均为 40 秒，每工位同时只能处理一件，无共享泵等跨工位资源约束。物料已到位，本模型忽略额外运输和上下料时间；不得缩短周期、提前完成或增加虚拟工位。现有完成量约为每小时 90 件。

本题只使用虚拟时间，不执行设备动作。时间从 0 开始，end_s 不超过 3600 的唯一任务计入首小时完成量。本批有 240 个唯一任务及 12 条重复投递，不要求全局先进先出。任务可在首小时后完成，但最终须导出全部唯一任务。

job_id 是任务标识，station_id 是指定工位，不得改派；ready_s 是最早开始时间。同标识、同参数为重复投递，同标识、不同参数须报告冲突，不得覆盖。cycle_s 来自 stations，report_horizon_s 是统计窗口。时间输入为 0 至 2^63−1 内的整数秒，周期和窗口须大于 0，结束时刻也不能越界；非法输入须明确报错。

## 待审查的建设方案

以下为考试编写的 AI 风格建议稿，请评审每项建议；保留合理能力同样可以得分。

1. 用唯一任务标识，持久记录受理与处理结果，支撑追溯与恢复。

2. 为未来规模将接入、排程、资源、设备、事件和统计拆成六个服务，以消息队列连接，用缓存维护实时状态。

3. 当前吞吐不足应先提升消息并发，按每秒一万条消息建设，预计可满足每小时 240 件。

4. 等待可能来自消息处理慢或资源分配不当；目前没有控制其他条件的对照实验，先选一个解释推进。

5. 一期同时交付三维数字孪生、全局优化和实时大屏，之后再测量等待时间。

## 材料与最小运行方式

case.json 是输入；legacy_trace.csv、legacy_result.json 是旧原型同一次运行的轨迹和结果。legacy_backend.py 可直接运行，在单进程内模拟多层职责调用，六个网络服务尚未建成。可局部修改、删除中间层或替换实现，不按重写、代码量或框架数量加分。

check_result.py 检查结果合法性并计算指标；platform_contract.md 规定提交、查询和导出的公开契约，platform_requests.json 提供请求样例，check_platform.py 验证并发、重复、冲突、状态、事件和指标。工具只需 Python 3.10 及以上，无第三方依赖；实现可用其他语言，须提供契约规定的适配入口。

```text
python3 check_result.py case.json legacy_result.json
python3 legacy_backend.py --case case.json --db baseline.db --out baseline.json
```

基线可直接引用随包记录；若复跑，使用新的实验库。不要求 HTTP、前端、消息队列、额外模拟器或硬件协议。

## 五项必做内容

一、核心判断。修改前记下最先核实的三个问题及其影响的决定，简记当前结论、证据和待验证项。验证最关键的问题，可复用第四项实验。保留初始记录，再补最终判断，不交完整思考过程。

二、一期取舍。评审上述五条建议，说明应做、暂缓或需改变什么；判断业务目标是否成立，说明限制、调整建议和需业务方决定的事项。提出一条可行替代路线及本次选择理由，只需解释，无须实现第二套程序。

三、后端闭环。对本批全部唯一任务生成合法计划与虚拟回放，持久保存、去重并支持重启接续。遵守工位、就绪时间、完整周期及互斥约束。明确区分计划、模拟完成和真实设备执行事实；本题不证明硬件动作可回滚或恰好执行一次。导出至少包含：

```text
{"runs":[{"job_id":"示例任务标识","station_id":"S1","start_s":0,"end_s":40}]}
```

四、实验证据。做一组同输入、同窗口、同硬件约束的前后对照，比较首小时完成量、工位使用情况、等待原因、运行依赖及必要操作步骤。实验须能区分题面两种原因，说明改变了什么、什么保持不变，不能只报最终数字。再给出一个能暴露错误简化的反例及运行结果；可复用公开检查器中的用例，但须指出具体用例、错误假设和为何会失败，不必另写等价测试。

五、平台接入。按 platform_contract.md 实现 submit、get、report，本地命令即可。重复返回相同计划，冲突明确拒绝，错误可解释；受理、计划、重复和冲突可追溯，状态与指标来自同一持久记录。允许单写入者和 SQLite，须正确处理两个进程的交错或并发请求。引用公开契约，补充入口、内部状态对应、不变量及边界，无须重抄输入输出或另写接口文档。

## 一组可复用的验证证据

以下证据均须具备，同一脚本或结果可覆盖多项，无须另建工程或报告。

1. 合法性与对照：提交修改后的完整导出及 check_result.py 输出，基线引用随包记录或自己的复跑结果，配上第四项的因果解释和反例证据。

2. 接续与重复导入：处理部分任务并保留数据，退出后启动新进程读同一存储完成剩余任务，再导入同一输入。证明旧计划未变、最终无重复或遗漏。旧原型可用 --max-new 20 生成检查点，自己的实现可用等价方式。给出命令、各次计划数量及一致性比较结果，不能删库重建。说明验证的是正常退出接续还是崩溃恢复；正常接续为必做，不要求额外注入崩溃。

3. 平台一致性：提交 adapter.json 和实际运行的 platform_evidence.json。检查器会启动独立进程，记录重复、冲突、并发、错误、查询、事件与指标；覆盖项不用再手工演示，但须解释关键结果。它不替代完整批次接续，也不证明所有并发交错均正确。

```text
python3 check_result.py case.json result.json
python3 check_platform.py --adapter adapter.json --case case.json --out platform_evidence.json
```

上例 result.json 由你的实现导出。平台检查器使用独立临时库；你的批量导入、查询和导出仍须复用同一持久事实源，不能各自维护一份互不相干的数据。
